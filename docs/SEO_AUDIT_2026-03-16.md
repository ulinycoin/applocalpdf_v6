# LocalPDF SEO Audit — 2026-03-16

## Scope

Audit covers:
- live site: `https://localpdf.online/`
- local marketing source: `website/`
- deployment config: `vercel.json`
- generated output: `website/dist/`

Working folder: `/Users/aleksejs/Desktop/LocalPDF_V6`

## Executive summary

LocalPDF already has a solid SEO foundation:
- clean crawlable marketing surface
- canonical tags on primary pages
- sitemap + robots present
- structured data on homepage, feature pages, and blog articles
- focused information architecture around core workflows

The main issues are not “SEO is broken”, but rather:
1. trust/technical signals are incomplete for a privacy-first product,
2. some schema choices are too aggressive or misfit the product model,
3. content architecture is still relatively shallow for feature-level capture,
4. legacy/noindex routes need clearer strategic handling,
5. on-page copy can be sharpened for intent matching and conversion.

## Key findings

## 1. Security/trust headers are incomplete

Observed headers on live site include:
- `Strict-Transport-Security`
- `X-Frame-Options: DENY`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy`

But missing / weak points:
- no `Content-Security-Policy`
- `Access-Control-Allow-Origin: *` appears on HTML response
- Python TLS verification hit a certificate-chain validation warning in local checks

### Why this matters
For a privacy-first PDF product, technical trust signals support both user confidence and brand credibility. Even when SEO ranking impact is indirect, weak trust posture can hurt conversions and perceived quality.

### Recommendation
- add a baseline CSP in `vercel.json`
- review whether HTML really needs `Access-Control-Allow-Origin: *`
- verify full TLS chain with an external SSL checker

Priority: **High**

---

## 2. Software/Product schema is too aggressive and partially misleading

In `website/src/layouts/BaseLayout.astro`, a global `SoftwareApplication` schema is injected across pages with:
- `price: 0`
- `priceValidUntil: 2026-12-31`
- `aggregateRating: 4.9`
- `ratingCount: 1250`
- merchant return policy / shipping details
- item condition fields

### Why this is risky
This looks more like ecommerce schema cargo-cult than an accurate software product model.

Potential problems:
- fabricated or unsupported rating/review data can create trust issues
- shipping and return policy fields do not fit a web app
- globally injecting app schema on pages like About/Privacy/Terms is noisy
- rich results eligibility may be reduced if schema feels inconsistent or spammy

### Recommendation
- remove ecommerce-specific fields from `SoftwareApplication`
- remove `aggregateRating` unless backed by real review data
- keep schema page-specific and realistic
- use:
  - `Organization` on company pages
  - `WebSite` on homepage
  - `SoftwareApplication` on app/feature pages only
  - `FAQPage` only where visible FAQ content exists
  - `BlogPosting` on articles

Priority: **High**

## 3. Homepage copy is strong strategically, but could match search intent better

Homepage positioning is clear:
- private PDF workflows
- local-first handling
- one workspace

But copy leans heavily on positioning language and repeats similar ideas:
- local-first
- no upload-first handoff
- trust up front
- one workspace

### Missed opportunity
For SEO, the homepage should more directly balance:
- brand story
- category definition
- task intent capture

Right now it is good brand copy, but slightly underpowered for broader query matching like:
- private pdf editor
- local pdf editor
- secure pdf editor
- offline pdf editor in browser
- pdf tools without upload

### Recommendation
Tighten homepage copy so it includes a more explicit query-intent layer near the top:
- what the product is
- who it is for
- what jobs it completes
- why it differs from upload-first tools

Priority: **Medium-High**

## 4. Feature coverage is good, but keyword surface is still narrow

Current canonical feature pages:
- `/features/edit-pdf`
- `/features/merge-pdf`
- `/features/ocr-pdf`
- `/features/compress-pdf`
- `/features/split-pdf`
- `/features/sign-pdf`
- `/features/convert-pdf`

There are also many legacy keyword routes redirected or rendered as noindex pages, for example:
- `/add-text-pdf`
- `/rotate-pdf`
- `/watermark-pdf`
- `/pdf-to-word`
- `/word-to-pdf`
- `/images-to-pdf`
- `/pdf-to-images`
- `/protect-pdf`

### Why this matters
Redirecting long-tail variants into broader canonical pages is valid, but only if the destination page deeply satisfies that intent.

Current risk:
- broad feature pages may not fully satisfy narrower search intents
- redirected terms can lose topical precision if supporting sections are too thin

### Recommendation
Choose one of two strategies per keyword cluster:

#### Option A — keep broad canonicals
Then each feature page must contain stronger subsections for variant intents:
- edit page: add text, rotate, watermark, organize pages, fill forms
- convert page: word↔pdf, images↔pdf, pdf→images
- split page: extract pages, delete pages
- security page: protect/unlock

#### Option B — create selected canonical long-tail pages
Create standalone indexable pages only for terms with real volume / commercial relevance.

Priority: **High**

## 5. Noindex/legacy strategy is partly good, but should be documented explicitly

Generated noindex pages include:
- legacy utility routes
- several old blog slugs/pages

Examples:
- `blog/add-text-to-pdf-guide.html`
- `blog/email-pdf-attachments.html`
- `blog/pdf-optimization-guide.html`
- `blog/protect-pdf-with-password.html`
- multiple tool aliases outside `/features/`

### Why this matters
The site currently mixes:
- 308 redirects in `vercel.json`
- static legacy pages with `noindex`

That can be fine, but the strategy should be intentional and documented.

### Recommendation
Define a route policy table:
- **redirect** when there is a clear replacement
- **410** when content is intentionally retired and has no equivalent
- **noindex page** only when the page still serves users but should not compete in search

Priority: **Medium**

---

## 6. Sitemap is clean, but minimal

`website/astro.config.mjs` uses an allowlist plus all `/blog/*` pages.
This is good because it prevents accidental indexation of junk routes.

What is missing:
- no image sitemap
- no `lastmod`
- no richer segmentation beyond a single sitemap file

### Recommendation
Not urgent, but later:
- add `lastmod`
- consider image metadata for blog/feature screenshots if search image traffic matters
- keep sitemap segmentation only if page count grows significantly

Priority: **Low-Medium**

---

## 7. Missing CSP and header hygiene are more urgent than micro-SEO tweaks

This is worth repeating: for LocalPDF, trust is part of SEO because trust is part of click-through and conversion.

A privacy-first product is judged on:
- copy
- security page quality
- technical headers
- consistency between promises and implementation

Priority: **High**

---

## 8. About / Privacy / Terms titles are functional but weak

Examples:
- `About | LocalPDF`
- `Privacy | LocalPDF`
- `Terms | LocalPDF`

These are not wrong, but they are weak if the goal is to capture trust-intent searches and reinforce relevance.

### Recommendation
Use more descriptive titles, e.g.:
- `About LocalPDF | Local-first PDF workspace`
- `Privacy at LocalPDF | Local-first PDF handling explained`
- `Security at LocalPDF | How LocalPDF handles private documents`

Priority: **Medium**

---

## 9. Internationalization is not actually deployed as localized SEO content

`vercel.json` contains redirects for `/de` and `/ja`, but there is no current `hreflang` implementation and no deployed localized content surface.

### Recommendation
Do not add `hreflang` until real localized pages exist.
If localization becomes a goal:
- create real localized canonical pages
- add reciprocal hreflang tags
- localize metadata and structured data where appropriate

Priority: **Low** right now

---

## 10. Blog exists, but topical clusters can be much stronger

The blog already covers useful topics, but to push SEO harder the content system should become more cluster-driven.

Good current directions:
- merge guides
- OCR
- compression
- security/privacy
- smart/AI workflow articles

Missing opportunity:
- explicit pillar-cluster mapping from blog → feature page
- clearer commercial-intent bridges from article to product workflow

### Recommendation
Build content clusters around each core feature:
- Edit PDF cluster
- Merge PDF cluster
- OCR PDF cluster
- Convert PDF cluster
- Security/Privacy cluster

Each cluster should have:
- one canonical feature page
- 3–8 support articles
- consistent internal links
- one clear CTA path into the app

Priority: **High**
