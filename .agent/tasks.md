## Сессия 2026-11-14 — Compress перестал быть пустышкой

Проверка перед правкой: прогнал текущий движок по корпусу (30 файлов) — он только пересохранял документ. Итог: **18.4 МБ → 17.5 МБ (−4.8%)**, медиана ~5%, у трёх файлов результат стал **больше** исходного; «Extreme» вообще отключал object streams, то есть делал файл крупнее. При этом Compress — второй по популярности инструмент (142 человека / 30 дней).

### Сделано

1. **Движок: реальное сжатие JPEG-изображений** (`compress-engine.ts`). Для DCTDecode-картинок: даунскейл до 1600 px (Balanced) или 1200 px (Strong) по длинной стороне и перекодирование в JPEG q0.72 / q0.6 через `OffscreenCanvas` в воркере. Текст не растрируется и остаётся текстом.
   Гейты, чтобы не сломать документ: пропускаются изображения с `SMask`/`Mask`/`ImageMask`/`Decode`, цвета не `DeviceRGB`/`DeviceGray`, картинки меньше 20 КБ; замена принимается только если она ≥10% меньше оригинала; любая ошибка декодирования оставляет исходный поток.
2. **Честность результата.** Если после сжатия файл не стал меньше, возвращаются исходные байты — пользователь никогда не получает файл крупнее. `updateFieldAppearances: false` при сохранении (не пересобирать формы, не падать на не-WinAnsi значениях).
3. **Пресеты переименованы по факту:** Light (только пересохранение), Balanced (1600 px), Strong (1200 px) — в панели Studio, в конвертере и в старом UI плагина. Подсказки говорят «JPEG photos», потому что Flate-картинки движок пока не трогает.

| `html-skia-type3.pdf` (44 JPEG) | 1003 КБ | **526 КБ (−48%)** | **468 КБ (−53%)** |
| `office-install-guide.pdf` (52 стр., текст) | 3578 КБ | 3499 КБ (−2%) | 3463 КБ (−3%) |

## Сессия 2026-11-13 (5) — защищённые PDF открываются в Studio (qpdf-wasm)

Триггер — 6 человек за 14 дней, которые загружали PDF с паролем и получали «No password given». Решение: не объяснять, а открывать.

### Сделано

1. **`@jspawn/qpdf-wasm` 0.0.2** (Apache-2.0, wasm 1.2 МБ) — единственная проверенная сборка qpdf без pthreads (вариант `qpdf-wasm@0.1.0` требует `Worker`/`SharedArrayBuffer` и COOP/COEP). Грузится лениво: пользователь, который не открывает защищённый файл, не скачивает ни wasm, ни 52 КБ скрипта.
2. **Дешифровка в воркере.** Новый command `DECRYPT_PDF` → `PDF_DECRYPTED`: qpdf-wasm работает в `worker-runtime`, канвас не блокируется (аудит `main-thread-forbidden` снова 0). Основной поток только читает расшифрованную копию и удаляет воркерный файл, чтобы не хранить дубль.
3. **Загрузка wasm без бандлера.** Пакет — Emscripten-UMD: при сборке в ESM он не находит свой `exports` и молча не инициализируется (проверено: чанки грузятся 200, wasm не запрашивается). Поэтому `qpdf.js` и `qpdf.wasm` отдаются как ассеты: в окне — `<script>` с `globalThis.exports`, в module worker — динамический `import()` того же файла. Оба пути проверены.
4. **Диалог пароля** (`use-protected-pdf-prompt` + `password-dialog`): остаётся открытым при неверном пароле («Wrong password. Try again.»), при отмене показывается прежняя инструкция, при успехе Studio импортирует расшифрованную копию.

- `npm run build`; `npm run audit:workerization:strict` — exit 0, `main-thread-forbidden: 0`.
- **Браузерный смоук (Playwright на preview-сборке):** загрузка `locked.pdf` → диалог; неверный пароль → «Wrong password. Try again.»; `secret` → диалог закрывается, в канвасе 1 страница с «LOCKED REPORT» (скриншот `.tmp/password-opened.png`, в git не попадает). Ошибки в консоли — только 404 от Vercel Analytics на preview.
- Не проверялось в проде до пуша.

## Сессия 2026-11-11 (3) — волна 2: CID-эмиссия, spike и решение

Цель волны 2 — рисовать правку кодами исходного Type0-шрифта, не встраивая ничего нового. Спайк закрыт: механизм проверен на живой накладной, границы измерены.

### Как это работает (и чем проще, чем ждали)

Identity-H пишет в поток **CID**, глиф = `CIDToGIDMap[CID]` (`/Identity` → глиф = CID), а связь «символ → CID» лежит в `/ToUnicode` самого файла. Значит для любого символа, который в subset уже есть, можно взять его CID и нарисовать `<CID…> Tj` **имеющимся ресурсом**: ни re-embed, ни слияния `/ToUnicode`, ни нового словаря — `/ToUnicode` уже отображает эти CID обратно в текст, поэтому строка остаётся извлекаемой.

Ширины — единственная часть, которая может потребовать правки словаря: неизвестный CID позиционируется по `/DW` (обычно 1000/1000 em). В замере **48 из 117** шрифтов вообще не нуждаются в правках, **35** — только в копии `/W` со ширинами из программы (по глиф-иду, не по кодпоинту: у subset'ов cmap часто вырезан).

Сделано: `src/services/pdf/text-edit/cid-text.ts` (+ 6 тестов) — разбор `/W` (обе формы записи), парсер `/ToUnicode` (bfchar + bfrange, обратное отображение), чтение программы (`FontFile2`), `encodeCidText`, `cidHexString`, ширины по глиф-иду. Декодирование потоков не зависит от рантайма: `DecompressionStream` → `pdf-lib/es/core` (в Node core отдаёт **сжатые** байты, поэтому его результат принимается только при изменившейся длине).

### Решение: **go, но узко**

1. Делаем только путь без правки словаря (символ есть в `/ToUnicode` и его ширина есть в `/W`) — 48 шрифтов / 14 документов. Копию `/W` не делаем в первой версии.

3. ToUnicode-merge не нужен и не делается (консенсус панели подтверждён замером).
4. Интеграция в applier — отдельная задача: рисование идёт `page.drawText`, а CID требует низкоуровневых операторов, поэтому нужно повторить ту же геометрию (поворот страницы, line height, выравнивание), что и сейчас. ### Найдено при живой проверке оффера (2026-10-08)
